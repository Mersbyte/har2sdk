# Security & privacy

## Reporting a problem

If you find a way for recorded data (cookies, tokens, personal data) to end up in generated files, prompts, MCP responses or mock responses, or a way for a crafted HAR file to inject code into a generated client, please report it privately through GitHub's **Report a vulnerability** button on the repository's Security tab instead of opening a public issue. Please do not attach real HAR files: describe the shape of the input or build a minimal synthetic one. `har2sdk inspect capture.har --json` replaces the values the leak guard knows about, but review it before sharing — see *Limits*.

## What har2sdk does to protect recorded data

The leak guard below is a heuristic. It links outputs back to the capture by matching recorded values (and a few forms of them) against the text it generates; it is not a proof that nothing leaked. The code and its reviews so far are AI-assisted (Claude Code, Codex, CodeQL); there has been no independent professional audit. A clean run means it found nothing it could match. Check `har2sdk inspect` and the generated files before committing or publishing them.

- The CLI and library make no network requests.
- **Leak guard.** Before generating anything, har2sdk collects
  - recorded values that look like data: ids with three or more digits or an id shape (`ord-77314`, `PROJ-7`), letter-only tokens that look random (judged by rare letter pairs and case flips: `KfTqLmZxRwPbNvYc`, `xkq-bvzt-rmn`), emails, phone numbers, long numbers, free text, URLs with query strings, relative paths with ids, secrets;
  - anything under a personal, secret or id key (`name`, `email`, `birthDate`, `token`, `id`, `orderNumber`…, with common Turkish, German, Spanish and French key words), CSV cells and XML elements under personal names, literals inside GraphQL documents (POST, GET and batched), and data inside query and form parameter *names* (`role[someone@…]`);
  - **names recorded in parts**: one-word values of sibling name fields in one object (`firstName` + `lastName`, `givenName` + `surname`, `vorname` + `nachname`, `isim` + `soyad`) joined in both orders with `-`, `_` and nothing (`zeynep-kaya`, `kaya_zeynep`, `zeynepkaya`), as identities;
  - **identities**: values under `login`, `username`, `owner`, `author`, `sender`, `reviewer`, `approver`, `id`… and in `x-user` / `x-tenant` / `x-org` headers, whatever they look like (`okilic`, `oguzs-clinic`, `ACME`), in any spelling (`ece_kaya` / `ece-kaya` / `ece.kaya`);
  - **labels**: one-word names of things (`"Books"`, `"Premium"`) found only under a `name`-like key of an object that doesn't describe a person. They are treated as data by the generator but not reported by the scanner (see below).

  The generator consults that set while deciding what may become code: a recorded id-shaped value or identity can't stay a path literal; dictionaries keyed by data or identities (or two or more same-shaped entries keyed by recorded values) become `Record<string, T>`, where a key that only mixes letters and digits (`thumb_200`, `fy2025`) counts as data when such keys are most of the object's keys, its only key, or recorded elsewhere, or when its value is an object or a list (`"parker2026": {…}` is an entry) — one with a plain value among ordinary property names (`"thumb_200": "https://…"`) is a property name; enum members must be vocabulary that is not recorded as data, a label, an identity or a word of a recorded personal name (`"zeynep"` when `"Zeynep Ak"` is a `fullName`; the mock fakes such words too), and only technical fields (`status`, `type`, `currency`…) get enums at all; query parameters whose names carry data are left out with a warning; cookie names and version metadata carrying recorded data are not listed; GraphQL string, list and block-string literals become variables, and so do numbers that look like data: under an id argument; under an identity argument (`customer`, `account`, `owner`) with three digits or more; integers of six digits or more; decimals of five digits or more or under a location argument (`lat: 41.0123`). Decimals become `Float` variables. The HAR file's name is not written into generated files.

  Afterwards every output is scanned:
  - `client.ts` and `openapi.json`: if a recorded value is found — as a token, as an identity inside a longer token (`remember_okilic`), as an identity of three characters or of several parts on its own or as a run of pieces of a compound token (`remember_lee`, `remember_ece_ak`; never inside a longer word: `sleeve` is not `lee`), percent-encoded, written with backslash escapes (a property key `synthetic\"secret`), or as an identifier form (`OguzKilic`) — the CLI writes **nothing** and exits with status 2, showing masked previews (`og…ev (email, 14 chars)`); `--allow-leaks` overrides. The MCP `generate_sdk` tool refuses the same way unless `allow_leaks` is set. Not reported: labels, labels of the API's own host names, and words har2sdk writes into every client (`ApiError`, `har2sdk`). With `--examples`, the examples in `openapi.json` are scanned too; only recorded dates and timestamps are not reported there, because the fake data keeps them on purpose;
  - the chat prompt, MCP responses, `inspect --json` and the CLI's endpoint overview, warnings and path-word list: everything the scan above would report is replaced with `<redacted>` (identifier forms with `Redacted`) — values, identities inside longer tokens, slugs and host names spelling a recorded name (`zeynep-ak.s3.amazonaws.com`), names a singular form shortened (`OguzDemirtaSetting`), and percent-encoded and backslash-escaped forms, and the method and type names built from an identity (`getRememberLee`). A test checks that scanning the redacted text finds nothing.
- What generated files *do* take from the capture: the base URL and any secondary origins, path segments judged to be resource names, property names, version/platform header values (`3.4.1`, `ios`), non-session cookie and header names, vocabulary-like enum values of technical fields (`"shipped"`), and GraphQL documents with their data-carrying literals turned into variables.
- `--examples` and the mock server serve **fake data with the recorded shape**, for JSON, XML, HTML, CSV and plain-text bodies: property names never change; ids, usernames and slugs are replaced with consistent same-shape fakes (salted per run, so they can't be reversed by hashing guesses; a fake never equals the recorded value), also in URL paths, in file names (`avatars/<user>.png`, `<user>_avatar.jpg`) and in host names named after a user; small numbers, timestamps and vocabulary under technical keys stay; large integers are faked; IPs become documentation addresses; names, free text, emails, phone numbers, personal dates (and calendar dates in a person's record), locations and URL query strings are masked; other words are faked. The mock also fakes the paths of superjson `meta.values` the same way as the payload's keys, replays only the media type and charset of a recorded `Content-Type` (not other parameters such as `profile="…"`), and scrubs unquoted HTML attributes (`value=okilic`) like quoted ones. `har2sdk mock --raw` serves the recorded bodies unscrubbed (JSON re-serialised, values unchanged). Bare strings (a top-level array item) are faked like other words, and a people collection's bare strings (`GET /api/users` → `["ece.kaya"]`) are identities. Every mock response carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, so a replayed page or XHTML document can't run scripts on the mock's localhost origin (with or without `--raw`).
- `har2sdk mock` listens on `127.0.0.1`, answers only `localhost`, `127.0.0.1` and `[::1]` Host headers (a page using DNS rebinding gets 403; with `--bind`, also the machine's own addresses and host name and any `--allow-host`), and allows CORS only from `localhost` and the recorded origins (with `--raw`, from `localhost` only). It reads request bodies up to 10 MB and answers 413 to bigger ones.
- The MCP server only reads `.har` / `.json` files, also when the path is a link (the link's target must be one); accepts a `base_url` only if it is one of the capture's origins or a localhost URL, since the client sends credentials there; writes only inside the HAR's folder, its working directory (not when that is `/` or the home folder) or the temp directory, checked on the real path (`realpath`); and refuses to overwrite a `client.ts` / `openapi.json` it did not generate. The CLI refuses the same (exit 1).
- Neither the MCP server nor the CLI writes through a symbolic link: a linked output folder, a linked folder between the allowed folder and the output folder (MCP), or a linked `client.ts`, `openapi.json` or `har2sdk.annotations.json` is an error. Files are written under a fresh temporary name and renamed into place, so a link created in between is replaced, not followed.
- Text from a HAR is always escaped in generated code; a hostile HAR must not be able to run code when the generated client is imported. In `openapi.json`, literal path text is percent-encoded as the client sends it (plus `'` and `*`), so quotes, backticks, `${` and braces from a recorded URL don't reach a path key that a downstream generator pastes into code.
- The generated client sends the token, API key, cookie, `headers` and the recorded default headers only to `baseUrl`'s origin (and `trustedOrigins`), on every redirect hop too: it follows redirects itself and checks each hop's origin (in a browser, which hides the target, it doesn't follow). `baseUrl` defaults to the origin the app sent its credentials to. In `openapi.json`, operations on another origin have `security: []`.
- Control characters (escape sequences such as OSC 52 "write to clipboard") are removed from everything the CLI prints, from the prompt it copies and from MCP responses; the CLI's own colours stay.
- What a model sees (the chat prompt, MCP responses) says that ids, paths, names and documents come from recorded traffic and are untrusted data, not instructions. GraphQL documents are shown without their `#` comments, and an `operationName` that isn't a GraphQL Name (`/^[_A-Za-z]\w*$/`) is ignored: the operation is treated as anonymous. A JSON-RPC or tRPC call whose method isn't an identifier (dotted, `/`, `:` or `-` separated, up to eight parts) is left out with a warning. Warnings show the paths of dropped requests with every segment that isn't a plain word masked as `{…}`. This makes a prompt injection planted in a capture harder, not impossible: paths and property names are still shown.
- The MCP server runs one `generate_sdk` at a time per output folder, so parallel calls can't lose annotations or leave a `client.ts` and `openapi.json` from different calls.

## Limits

The leak guard is a heuristic that matches outputs against the capture, so anything it can't match gets through. Evidence is read from the parts of the capture the collector parses: JSON bodies (any media type with "json" in it, such as `application/x-amz-json-1.1`), form and multipart fields (non-file parts, with quoted or token field names; JSON inside a field too), CSV, XML / HTML bodies, the JSON written into a page's scripts (as code, or as a string: `JSON.parse("…")`, Next.js flight data), JSON in HTML attributes and the values of `<meta>` / `<input>` name–value pairs, NDJSON / JSON Lines and server-sent events (an event's `data:` lines joined), query strings, request headers, response headers (those named after a person or account, such as `x-user` or `x-account-email`; of the others only values that are data by their shape, such as an email or an id, and of `location` only the query string), cookies (as sent, and decoded once and unquoted, under their names; Express `j:` JSON and `s:` signed values unwrapped), Basic credentials, GraphQL variables under the argument they are passed to (in POST bodies, form fields and GET query strings; comments and strings in the document are not bindings), and WebSocket text frames (also in Socket.IO, SockJS, SignalR and STOMP framing) — of every request except static assets (scripts, styles, images, fonts; a beacon, a CSP report or any asset request with a body is read), including trackers, pages and hosts `--host` leaves out. It does not read binary WebSocket frames, protobuf or other binary bodies, the code of scripts (only JSON written into them), `referer` and other browser headers, or a redirect's path. Identity keys (`login`, `owner`, `author`…) are recognised in English, Turkish, German, Spanish and French (not French `identifiant`, which is any record's identifier). Some keys are weak evidence: a plain word under `from`, `to` or `by` counts as an identity only until the capture has a top-level endpoint of that name (the path's last segment, right after the API root or a version: `/api/v1/search`, `/orders`), however often it is seen that way, and a strong source (`login`, `owner`…) always wins; a plain word under a bare `ref` or `number` key (`?ref=main`) is vocabulary, not an id, while `reservationRef` or `orderNumber` name a record; `sort_by` / `orderBy` (exactly those two words) name a field, `last_order_by` is an actor; and a value with a "/" in it (a route) is never an identity. It cannot recognise a value that has no evidence in those parts — a plain word that appears once, as a path segment, never echoed by a response, never listed by a collection and never stored under a personal or identity key. Such a value can become a path literal and a method name, and appears in `inspect` output. So that the user can judge such words, the CLI (after the files it wrote), `har2sdk inspect` (and `inspect --json`, as `pathWords`) and the MCP `analyze_har` and `generate_sdk` responses list every literal path word written into `client.ts` (not the API root or version segments), with the number of distinct recorded paths that use it, the ones seen in only one path first. The list is advice, not a guarantee: it changes nothing in what is generated or refused, it doesn't say which words are names, a word seen in several paths can still be personal data, and only path segments are listed (not property names, GraphQL operation names or RPC procedure names). In MCP responses and `inspect --json` the list is redacted like everything else there, so a word the guard does know shows as `<redacted>`. A one-word name of a thing (a repository, a project, a category) counts as vocabulary unless the capture lists it as a member of the collection its path segment follows. The mock serves such unrecognised values in text bodies as recorded only if they look like vocabulary. Lengths count a letter without case (Chinese, Japanese and Korean characters, Arabic and Hebrew letters) twice and every other character once, so a two-letter Chinese name is data under a personal key while a three-letter `firstName` in a cased alphabet ("Ali", "Лев") is not collected and can stay a path literal. Fakes replace letters, marks and digits of every script with characters of the same Unicode category; at a block edge one can come from a neighbouring script. Random-looking tokens without digits are recognised by letter statistics: long mixed-case tokens almost always, short or lower-case ones (`xkqbvtrm`) only about half the time, and a camel-case name made mostly of acronyms can be taken for one (it then becomes a path parameter). Digits are recognised in every script (`\p{Nd}`: Arabic-Indic, Devanagari, full-width…), in values and in dictionary keys (`"דוד-12"`); version strings and issue keys (`PROJ-7`) are still ASCII only. Names in parts are joined only between one-word values of name fields of the same object (up to four fields); a name split across objects or requests isn't. An email's local part (`okilic` in `okilic@corp.example`) is also an identity on its own, unless it's a role mailbox (`info`, `support`…), since apps commonly reuse it as a username elsewhere; one known only that way is dropped again when the capture has a top-level endpoint of that name (`cart@supplier.example` next to `GET /api/v1/cart`; not `/inbox/cart`). The words of a personal name of two to four words are joined with `-`, `_`, `.` and nothing, also without diacritics, into identities, however short the words (`Ece Kaya` → `ece-kaya`). GraphQL numbers are lifted by the rules above: a short integer under a neutral argument (`pin: 4321`) stays in the document, as do enum literals, aliases and fragment names.

Not caught yet: a recorded value the app rewrites before using it — decorated (`🌸zkaya🌸` recorded, `zkaya` in a path), with zero-width or other invisible characters, in another Unicode normalization (NFC recorded, NFD in a path), or as a part of a longer compound name (`seen_by_zeynep`, `last_viewed_by_zeynep`) unless it is an identity; one-word names used as dictionary keys (`{ "zeynep": 10, "mehmet": 7 }` becomes properties of a type, also in the prompt, MCP and the mock); names inside an encrypted JWT (JWE) or a JWT split across cookies (since 0.6.17 the claims of a JWT, wherever it is recorded, are read as evidence about its user); values longer than 4,000 characters, which are never collected. The guard also reads only part of a very large capture for evidence: the first 2,000 items of an array, JSON nested up to 64 levels, the first 200 KB of a text body and the first 5,000 rows of a CSV. Evidence beyond those limits (a login at array position 2,500) isn't collected. A JSON body nested deeper than 200 levels isn't parsed (its type is `unknown`). The `query`, `extensions`, `operationName` and `method` keys of a body are skipped as GraphQL or JSON-RPC structure only when the body is that kind of envelope (a GraphQL document, an `operationName` or `variables`, a persisted-query `extensions`, a `jsonrpc` field); in any other body they are data. A recorded identity of three characters is matched only as a whole token or as whole pieces of a compound token, so `lee` is found in `remember_lee` but not in `sleeve`; in `client.ts` the CamelCase names built from it are not reported on their own (the path literal they come from is).

Review `har2sdk inspect` and the generated files before publishing generated code. Treat `.har` files like passwords.

These behaviours are covered by the test-suite: `test/review*.test.ts`, `test/edge.test.ts`, and `test/privacy-fuzz.test.ts`, which generates a random person and a capture from a random subset of placement types with key names drawn from pools in five languages, and checks every output including a real MCP session and every mock response (30 seeds by default; the long run, `HAR2SDK_FUZZ_SEEDS=1000`, passes). The placement types and key-name pools are lists written by the authors; the test is evidence, not a proof.

## Acceptable use

har2sdk is meant for APIs you own or are allowed to use. Automating someone else's private API can violate their terms of service. Don't use it to access data you're not authorised to see, and don't publish generated SDKs for other companies' services.
